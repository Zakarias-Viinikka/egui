Plan, roughly in the order I'd do it:

Stage 1 — stop polling, listen for the window being born. Instead of querying the tree every 100ms and matching by name, select SubstructureNotifyMask on root and block on wait_for_event() for a CreateNotify whose parent is root. That event fires the moment XCreateWindow happens, before any properties are set and long before MapWindow. Since your app only creates one top-level window at startup, the first such CreateNotify you see is it — no name lookup needed.

Stage 2 — win the race that actually matters. The instant you get that CreateNotify, call ChangeWindowAttributes with override_redirect(1) on that window ID, before touching anything else. Because override_redirect flips before MapWindow is ever called, the server never redirects the map request to the WM at all — the window just appears, unmanaged, from the start. This is the fix that makes the whole thing not a hack: you're not un-managing a window the WM already adopted, you're preventing adoption in the first place.

Stage 3 — critical setup detail, not optional: the connect() and the change_window_attributes(root, SUBSTRUCTURE_NOTIFY) call have to happen synchronously in main(), before eframe::run_native() is invoked — not inside the spawned thread. X only delivers events to a client that was already selecting for them when the event occurred; if the event-mask registration is still in flight on a background thread when eframe creates its window, you can miss the CreateNotify entirely and you're back to nothing happening. So x11_overlay::apply() needs to do the connect + event-select part inline, then spawn only the blocking wait_for_event loop off to a thread.

Stage 4 — once override_redirect is winning pre-map, the reparent-to-root trick should become unnecessary, since there's no WM-imposed frame or cached compositor state to shake loose — you set the empty XFixes input shape once, on a window the WM never touched, and it should just hold. Try dropping the reparent step and confirm click-through survives; if it does, that's confirmation the original problem (WM/compositor caching against a managed window) is actually gone rather than papered over.

Stage 5 — you lose _NET_WM_STATE_ABOVE as a mechanism, because the WM isn't managing the window anymore to honor it. Replace it with ConfigureWindow using stack_mode: Above, called once right after map. If something else can later draw over it (another window raising itself), you'd re-assert stack-mode Above from the same watcher thread whenever it sees a new sibling CreateNotify — same event loop, one more branch.

Fallback, only if Stage 2 turns out to lose the race in practice (i.e. winit maps faster than your handler can react): the bulletproof version is creating the X11 window yourself with override_redirect baked into the original CreateWindow call — atomic, no race possible — and wiring egui to render into that window via wgpu/glow and raw-window-handle instead of letting eframe create the window. That's a real rewrite, not a patch, so worth trying stages 1-5 first and only falling back to it if testing shows the CreateNotify handler isn't consistently fast enough.
