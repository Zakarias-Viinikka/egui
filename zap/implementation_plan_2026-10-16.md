## Step 6: Fix the .sh/.toml approval

Files: zapgui/app_core/src/terminal_router/file_trust.rs, zapgui/app_core/src/chain/play.rs, zapgui/app_core/src/terminal_router/route_requests.rs, zapgui/app/src/egui_setup/drawing_requirements.rs, FILE_TRUST.md.

The approval answers the wrong question. is_approved reads the file as it is on disk and compares its hash with the stored one. record_approved runs after a confirmed write and stores the hash of the file as it is on disk at that moment, which is the content that was just written. From then on the disk content equals the stored hash until someone touches the file, so every later chain passes the check whatever it writes, and a whitelisted folder applies it without review. The entry has to mean "this exact content may be written at this path", not "the file is in a state the user once accepted".

The new key is the content being written. An entry still holds the path, a hash and a time, but the hash is the hash of a write, and the question is asked before the write happens. is_approved takes the path and the hash of the text the chain would leave in that file. It applies the drift rule first: if the file on disk no longer hashes to the stored value, something other than zap changed it after the approval, so the entry is deleted on the spot and the answer is false. Otherwise it answers true only when the stored hash equals the hash of the write. A file deleted out of band hashes as empty input and revokes its entry the same way. The consequence is intended: a changed .sh or .toml is always reviewed, and an entry only short-circuits a write of exactly the content it recorded.

A chain can touch one file in several steps, and each step's after text is the whole file at that point, so the write that matters is the last one. Chain gets a method final_writes(wanted) in play.rs. For every path written by create, replace, overwrite or append it returns the path and the after text of the last such step that is wanted and not a no-op. wanted follows the writer's rule: a missing entry counts as true, so an empty slice means every step. Steps that write no content (zaprm, zapmv, mkdir, rmdir, cargo, run, and the chmod step of step 7) never appear. Both sides of the approval use this one method: the check before the write passes an empty slice, and the record after confirm passes the real wanted.

file_trust changes shape to match. all_approved takes the list of path and text pairs, ignores paths that are not sensitive, and hashes each text with the sha helper that run_trust already exports. record_approved takes the same list and stores the hash of each text, never sha_of_current, so a step that was not written records nothing. sha_of_current stays, for the drift rule only. Give the store functions variants that take the folder as a parameter (load_in, save_in, remove_in, is_approved_in, record_approved_in), with the existing names calling them with config_dir(), so tests run over a temp folder and never touch the user's real approvals.

Call sites. In route_requests.rs, handle_chain replaces its sensitive_paths block with all_approved over final_writes. handle_overwrite, which today has no sensitive-file check at all and would auto-apply a bare overwrite onto an unapproved .sh inside a whitelisted folder, gets the same call. In drawing_requirements.rs, refresh_trust_after_chain_confirm takes wanted and records final_writes(wanted) instead of every step path that is not a delete, which also stops a marked .toml step from being recorded as approved with its old content. Retry chains always go to review and need no change. Entries written by the old rule need no migration: they only match an identical write, and the first drift deletes them.

Rewrite FILE_TRUST.md in this step. It must say that the key is the path plus the hash of the content being written, that the check runs before the write, that a chain's write is its last content-writing step per file, that an entry is deleted when the file on disk stops matching it, that a changed write is always reviewed, what else removes an entry (zaprm, zapmv, rmdir), that run_trust and file_trust stay separate, and where the code lives.

Tests: in file_trust.rs over a temp folder: no entry gives false; after record_approved with a write while the disk holds that text, is_approved is true for that hash and false for any other hash, which is the regression for the reported bug; a file changed out of band makes is_approved false and deletes the entry, and restoring the old text does not bring it back; a deleted file revokes; record_approved skips non-sensitive paths and stores the hash of the text it was given, not of the disk. In play.rs: final_writes keeps the last step per path, drops no-op steps, drops zaprm, zapmv, mkdir and rmdir steps, falls back to the previous wanted step when a later one is not wanted, and treats an empty slice as every step.

Done when: a chain that edits a .toml inside a whitelisted folder goes to review; after confirming it, a second chain with different content for the same file goes to review again instead of applying; a bare overwrite onto a .sh in a whitelisted folder goes to review; marking the .toml step and confirming records nothing for that file; FILE_TRUST.md describes the new key; c t passes.

## Step 8: Single-file whitelisting and hidden files

Files: zap_wire/src/hidden.rs (new), zap_wire/src/lib.rs, zap_wire/src/config.rs, zap_wire/src/chain.rs, zapgui/app_core/src/chain/whitelist.rs, zapgui/app_core/src/last_change.rs, zapgui/app_core/src/terminal_router/route_requests.rs, run_file.rs, cargo_run.rs and retry.rs in the same folder, zapgui/app/src/egui_setup/drawing_requirements.rs, zapcli/app_core/src/general_util/path_parsing.rs, zapcli/app_core/src/command_router/mod.rs, and core_commands/cat.rs, head.rs, tail.rs, wc.rs, ls.rs, cd.rs and last.rs.

Single-file whitelisting. A line in whitelist.txt stays an absolute path. What it points at decides how it matches, and that is decided at match time: if the resolved entry is a file, a candidate matches only when its own resolved path is that file, so nothing beside it or below it matches; if the entry is a folder, or does not exist, it matches by whole path components as today. In whitelist.rs is_inside is renamed is_whitelisted, since it no longer means inside, and branches on the entry's kind; its callers are the two sites in route_requests.rs, and step 9 adds a third. validate_add accepts a regular file as well as a folder, still refuses / and the home folder itself, and also refuses a path that the hidden list hides. A whitelisted .sh or .toml file still goes through the approval of step 6; being whitelisted never skips it. The menu tags each entry as file or folder, and its add field says folder or file.

The hidden list. It is hidden.txt in the zap config folder (honouring XDG_CONFIG_HOME), read with the line-list reader from zap_wire::config, so comments and blank lines are ignored and a missing file is an empty list. A line has one of two shapes. A path, starting with / or ~/, hides that file or folder and everything under it. A bare name with no slash hides every path that has a component of that name at any depth, so the line .env hides every .env file. Matching is by whole components, never by string prefix: a hidden /a/secrets does not hide /a/secrets2.

The matcher lives in zap_wire/src/hidden.rs, std only like the rest of zap_wire. HiddenSet is built from the list, and each path entry is kept in two forms: the lexical form (tilde expanded, . and .. collapsed) and the resolved form (the nearest existing ancestor canonicalised and the remaining components appended, the idea behind resolve_existing_parent in whitelist.rs). is_hidden(path) builds the same two forms for the candidate and answers true when either form lies under any entry form, or any component of either form equals a name entry. The lexical form catches a create inside a hidden folder that does not exist yet and a path written with ..; the resolved form catches a symlink in a visible folder that points into a hidden one. Hidden always wins over the whitelist. refusal(path) returns the line "deliberately hidden by the user: /abs/path", built from the path as the caller wrote it made absolute, never from the resolved form, which could reveal where a symlink points. check(path) loads the set fresh on every call and returns that line when the path is hidden, so an entry added in the menu applies to the next command with no restart.

The chain parser enforces it. zap_wire::chain gets ParseConfig, which holds the HiddenSet (step 10 adds the extension list to it), parse_with(input, config), and parse(input), which loads the real config and calls parse_with, so every caller keeps calling parse and none can skip the rule. The tests module in chain.rs defines its own private parse that calls parse_with with an empty config, which shadows the glob import, so the existing tests do not change and never read the user's files. The check runs at the points where a path is already validated, so the error carries the step's line: the absolute-path helper for zaprm, zapmv, mkdir, rmdir and chmod, parse_path_and_flags for create, replace, overwrite and append, the cd folder, and the file argument of run. A cargo step is covered through its cd folder. The message is the refusal line, so zapcli reports "zap: nothing was sent. line 3: deliberately hidden by the user: /abs/path." zapgui parses again with the same function, so a client that skipped zapcli is still stopped. handle_retry also checks the steps it carries over from the saved record, because those were parsed before the entry existed.

The zapcli commands. cat, head, tail, wc, ls and cd resolve their path argument through path_parsing.rs; put one call to hidden check right after that resolution, so a hidden path prints the refusal as an error line and does nothing else. cat also puts the refusal line on the clipboard in the file's place under its === path === header, so a paste-back explains the gap, and still copies the other files. cd refuses a hidden folder and any folder inside one, which is what stops cd followed by relative reads. ls of a hidden folder refuses; ls of a visible folder leaves hidden children out of the listing without a word, so the AI never learns they exist. run and cargo refuse when the file or the working folder is hidden, in zapcli before the socket opens and again in run_file.rs and cargo_run.rs in zapgui. last in zapgui (handle_last) refuses a hidden path it was asked about; with no argument it skips hidden records, which needs last_change to offer a most-recent lookup that takes a filter. The command files, path_parsing.rs, last_change.rs and retry.rs were not visible while planning; read them first and keep each command's existing output style.

The menu. The whitelist menu gets a second section, Hidden files, under a separator, shaped like the folder section: a list with a remove button on each entry, an add field with the hint "absolute path, ~/path or a bare name", and an error line of its own. The state is three new fields beside menu_folders, menu_draft and menu_error, loaded in open_menu and saved through the line-list writer the moment an entry is added or removed (the write drops comment lines, as the whitelist save does today). Adding refuses an empty line, /, ~, the home folder and a path with .. in it; it accepts a path that does not exist yet and any bare name. The panel scrolls vertically now that it can grow, with both sections inside one scroll area.

Tests: in hidden.rs over a temp config folder: a file entry hides exactly that file; a folder entry hides itself and everything under it at any depth; a bare name hides any path with that component and nothing else; /a/secrets does not hide /a/secrets2; a path written with .. that lands in a hidden folder is hidden; a symlink in a visible folder to a hidden file is hidden; a path that does not exist under a hidden folder is hidden; ~/ entries expand; comments and blank lines are ignored; a missing or empty file hides nothing; refusal names the path as written and uses the exact phrase. ## Step 9: Partial approval for a mixed chain

Files: zap_wire/src/chain.rs, zapgui/app_core/src/chain/play.rs, writer.rs, whitelist.rs, zapgui/app_core/src/terminal_router/route_requests.rs, retry.rs in the same folder, zapgui/app/src/egui_setup/drawing_requirements.rs. This step uses steps 6, 7 and 8.

Why one zaprm shows everything today. handle_chain makes one chain-wide decision: apply every step without review, or send every step to review. One zaprm anywhere makes it review, so the window shows all steps, including the whitelisted edits the user already trusts. The decision becomes per step, and the window shows only the steps that need eyes. The write does not change at all: Confirm still applies every step that is not marked, in order, all or nothing, and Deny All still writes nothing. The steps that are not shown are written together with the ones that are.

The field. Chain gets review_indices, a sorted list of real step numbers, zero-based like the steps list. Empty means every step is shown. play_forward leaves it empty and the caller sets it, so every other place that builds a Chain, retry included, gets "show everything" without a change; the compiler points at each struct literal that needs the new field. The surface review window has its own data type and never reads the field.

Which steps need eyes. A function in play.rs takes the chain, the whitelist entries and an unapproved lookup (a closure from a path and its final text to true when the path is a .sh or .toml file and that write is not approved, so the chain module does not depend on terminal_router) and returns the sorted indices of the steps that need eyes. There are three kinds of reason. A verb reason: the step's verb is always reviewed (zaprm, zapmv, rmdir, chmod, cargo, run). A whitelist reason: the step's path, or for a move its destination, is not matched by the whitelist, where a whitelisted file entry counts from step 8; mkdir is judged by its own path, because a mkdir has no snapshot, and today a mkdir outside the whitelist rides along unnoticed with whitelisted edits. An approval reason: the path's final write, from final_writes, is rejected by the unapproved lookup. An empty whitelist is a whitelist reason for every step. A verb reason marks that step only. A path reason (whitelist or approval) marks every step that touches that path, because the user cannot judge the last edit to a file without the earlier edits of it in the same chain. Chain::needs_review stays as the verb-only rule.

What the caller does with it. The function's empty result means nothing needs eyes, so the chain auto-applies as a fully whitelisted chain does today; the field's empty value means the opposite, show everything, and one must never be passed into the other. handle_chain maps the result three ways: empty applies at once; a result that holds every step stashes the chain with the field left empty; anything between stashes it with the field set to the result. handle_chain_run does the same mapping before it wraps the chain in an Arc, so a chain of whitelisted edits ending in cargo or run shows the run step and any edit that needs eyes, and nothing else. handle_overwrite uses the same function on its one-step chain. handle_retry leaves the field empty on purpose: a retried chain is one the user already chose to look at.

The window. All per-step state stays indexed by real step number: marked, visited, verified, allowed and the click guards. Three things use the visible list instead: the column of blocks, the step shown when a chain arrives (the first visible one), and the count in the caption. A small pure function visible_steps(chain, revealed_all) returns every step when the field is empty or revealed_all is set, and the field otherwise. show_blocks becomes "more than one visible step", so a lone zaprm shows no block column, like a one-step chain today. A block's click shows that block's real step. The caption keeps real numbers, so the lone zaprm of four reads step 4 of 4, which matches the failure report and the numbers retry takes; when steps are hidden it gets a muted suffix, "· 3 more steps in whitelisted folders are written with this one". The boundary chip still reads the whole chain, since it was computed over every step. A hidden step can never be marked, so wanted is true for it. How a mark interacts with a later step on the same file is step 18's business, and this step does not change it.

A hidden step that goes stale. Decision: a hidden step that fails at confirm is revealed, not rejected silently. A check before the window opens would run milliseconds after play_forward and catch nothing, because the window stays open for minutes while a whitelisted chain or the user's editor can change a file, so only the check at confirm sees it. writer::apply already refuses, before writing anything, when any snapshot differs from the disk, so atomicity does not depend on this decision; what changes is what the user sees. Nothing is closed and nothing is cleared: the chain is dead, because its snapshots never refresh, so the user's next move is Deny All and then retry, and seeing the step that went stale is what lets him choose. ## Step 10: Extension allowlist

Files: zap_wire/src/chain.rs (ParseConfig, parse); the two places that build a ParseConfig (zapgui's crate::chain::parse wrapper that route_requests.rs calls, and zapcli's chain command; wherever step 8 loads the HiddenSet, load the allowlist beside it); zapgui/app_core/src/terminal_router/route_requests.rs (handle_overwrite only); CHAIN_CHEATSHEET.md. No new source files. ~/.config/zap/extensions.txt is a user file the code reads and never writes.

The allowlist is a small type, ExtensionAllowlist, defined in zap_wire next to HiddenSet and stored as a field of ParseConfig. It has two constructors, from_text(&str) (pure, for tests) and load() (reads $HOME/.config/zap/extensions.txt), and one query, check(verb, path), which returns the finished error message rather than a bool. That way parse and handle_overwrite share one wording and one rule.

File format. One extension per line, lenient about spelling: split on newlines, commas and whitespace, drop everything after a #, strip one leading dot, lowercase. An entry is valid when it is 1 to 16 ASCII letters, digits, _, - or +; invalid tokens are skipped. A missing file, an empty file and a comments-only file all mean an empty list, and an empty list allows everything (the opt-in rule).

Read it on every parse, in both binaries. zapgui is long-running and zapcli is not, so a cached copy would let them disagree after an edit. zapcli rejects early so a bad path never reaches the socket; zapgui re-checks because it is the authority.

Fail closed on a broken file. Two situations must never silently turn into allow-everything: the file has tokens but none is valid (say .rs;.md on one line), or it exists but cannot be read for a reason other than not-found. Both give a broken allowlist that refuses every checked verb and tells the human to fix or delete the file.

What counts as the extension. The text after the last dot of the final path component, lowercased. Path::extension does this lexically (no filesystem access, so ~/ paths work), returns none for dotfiles like .gitignore, and returns an empty string for foo.; treat empty as none.

Per verb.

| Verb | Rule |
| --- | --- |
| create, replace, overwrite, append | the path needs an allowed extension; extensionless paths are refused whenever the list is non-empty |
| zaprm, zapmv, mkdir, rmdir, chmod, rename | any path, nothing checked. That includes zapmv and rename destinations, so a rename can change the extension. Accepted on purpose: both verbs are always reviewed and the caption shows the new name |
| run, cargo, astgrep | bypass: the exec bit and trust gate cover run, cargo writes no path, astgrep only ever touches .rs files |

Where it runs. In parse's create/replace/overwrite/append arm, right after parse_path_and_flags produces the path, which is after the body was consumed. That order matters for step 11: the cursor is already past @end when the error is recorded. Call check from one place and let the surrounding code decide what to do with the message. In step 10 that is an early return like its neighbours; step 11 turns it into a collected error. The error's line is the header line.

Wording. Disallowed: "create: .txt files are not allowed here, allowed extensions are .rs, .md, .toml." Extensionless: "create: /abs/Makefile has no extension, and only paths with an allowed extension can be written (allowed: .rs, .md, .toml)." Broken file: "create: ~/.config/zap/extensions.txt has entries but none are valid extensions, fix the file or delete it to allow everything." Show at most 12 extensions, then an ellipsis. Never put a semicolon or a newline in a message: step 11 joins messages with semicolons.

The hole to close. handle_overwrite in route_requests.rs builds its Step by hand and never calls parse, and zap overwrite <path> plus a newline and the content reaches it through zapcli's zap passthrough. Without a fix the allowlist is a suggestion. Make it call the same check with a freshly loaded allowlist right after its absolute-path check and return "zapgui: overwrite refused: <message>". While you are in there, look at whether step 8 applied the HiddenSet in that function. If it did not, do not fix it here; put it in the final report.

Retry. retry rebuilds chains from steps that were already parsed and is not re-checked. The human is asking for the retry and sees the path. Leave it alone.

Docs. Add an "Allowed extensions" section to CHAIN_CHEATSHEET.md. The AI never sees the list, so say that the error names it. Give the per-verb rule in a sentence each, and note that with a list set, names without an extension (Makefile, .gitignore) cannot be written.

Tests: from_text handles comments, blank lines, leading dots, uppercase, commas and duplicates; an invalid token is skipped; only invalid tokens means broken; empty and comments-only mean allow-all. In parse with rs and md allowed, /tmp/a.rs and ~/a.MD pass, while /tmp/a.txt, /tmp/Makefile, /tmp/.gitignore and /tmp/a. are refused for each of create, replace, overwrite and append, and the message names the extension and lists the allowed ones. Same list: zaprm, zapmv, mkdir and rmdir accept /tmp/Makefile; cd /tmp then run /tmp/x.sh, and a cargo step, pass. Steps 7 and 12 add the same assertion for chmod and rename. A broken allowlist refuses everything checked and says to fix the file. Default ParseConfig: every existing parse test passes unchanged. check itself gets its own test with a temp allowlist, as the stand-in for the handle_overwrite guard (the route reads HOME; do not mutate env in parallel tests).

Done when: with rs and md in extensions.txt, pasting create /tmp/x.txt into zapcli prints the refusal without touching the socket, zap overwrite /tmp/x.txt is refused by zapgui, and deleting the file restores today's behaviour. All existing tests pass and the cheat sheet is updated.

Part A, hints on failed steps. Where a hint attaches: not inside apply_step, which stays pure and keeps its messages because the writer may call it again at write time. play_one wraps apply_step's Err with a hint call, and its own "does not exist" errors (zaprm, zapmv, rename) call the same helper. A hint is one parenthesised clause appended to the existing reason, so "step N of M (verb path) failed: ..." and play_forward's semicolon join are untouched. A hint never holds a newline or a semicolon of its own; file text it quotes is trimmed, cut to 80 characters and set in backticks.

Replace, zero occurrences. Everything runs on the text the replace actually saw: the in-memory text after earlier steps, not the disk. Three tiers, first that applies wins. Whitespace only: trim both ends of every line (this also drops a stray carriage return) on both sides and look for a run of file lines equal to the old lines; if found at line N, say the old text matches there when indentation, tabs or line endings are ignored, which is the most common real failure and costs no scoring. Closest line: anchor on the old-text line with the most token weight (characters in its tokens, from tokenize; the first line wins ties); score every file line against it with similarity, and the best score at or above SIMILARITY_THRESHOLD is the hit, earliest line on ties. For one-line old text, name the line number and show the line; for longer old text, shift it so its anchor sits on the hit, walk the old lines against the file lines from the top (trimmed), and name the first old-text line that differs with the file's text at that spot, or say the file ends before that old-text line if the walk runs off the end. Nothing close: best score below the threshold says no line in the file is close, so the path may be wrong; an old text with no tokens at all (just a closing brace, say) gets no hint. Cost guard: no hint on files over 20,000 lines, and skip file lines over 500 characters; at those sizes no prefilter is needed.

Replace, wrong count above zero. Add the starting line of up to five matches: "found 3 (at lines 12, 40, 77)". The AI can then add context to its old text or use xN.

Create when the target exists. current is already in hand: say how many lines it has and what it starts with, and that overwrite replaces it. No scoring.

Does not exist (overwrite, append, replace, zaprm, zapmv, rename). One helper. Candidates are the parent folder's entries on disk plus files earlier steps of this chain created there. Suggest the closest name by edit distance: equal ignoring case wins; otherwise a distance of at most 2 or a fifth of the name's length; ties alphabetical; scan at most 5,000 entries. If the parent folder is itself missing and no earlier mkdir in the chain makes it, say that and name the nearest existing ancestor instead. The edit distance lives in similarity.rs next to the line scorer, because the token similarity there scores a mistyped file name near zero.

## Step 13: Identifier rename with ast-grep

Verb and grammar. astgrep rename <folder> <old> <new>: one line, four tokens through argv::split. rename is the only subcommand for now; the extra word leaves room without a new verb. The folder is absolute or starts with ~/. Old and new are plain ASCII identifiers: a letter or underscore first, then letters, digits or underscores, not _ alone, and neither a Rust keyword (one const list next to the parser: a keyword as the new name would not compile, and as the old name it matches no identifier node). Old and new must differ. Restricting to identifiers also means nothing from the chain can reach the rule text or the regex inside it. At most one astgrep step per chain, because a second would read a disk that does not yet hold the first one's result. A trailing cd plus cargo check after it is fine. Storage reuses Step fields: path is the folder, old_text the old name, new_text the new one; update those field comments and add no field. Messages, collected like any parse error: "astgrep: only rename is supported", "astgrep rename: needs a folder, the old name and the new name", "astgrep rename: X is not a plain identifier", "astgrep rename: X is a Rust keyword", "astgrep rename: the new name is the same as the old one", "astgrep: only one astgrep step per chain", plus the usual absolute-path message.

Ambiguity, as accepted. Every identifier with that spelling changes: locals, fields, methods, types, and same-named symbols in other modules. Say so in the cheat sheet, with the blind spots: strings, comments and doc comments are untouched, and so are inline format arguments such as {name}; only .rs files are read; target and dot-directories are skipped; renaming a module does not rename its file (a later paste does that with rename).

Where the binary comes from. The installed ast-grep executable, run as a subprocess and used strictly read-only. Not the library crate: it brings tree-sitter grammars (C builds) and an API that shifts between 0.x releases into the app that most needs to stay quick to build, and an installed binary updates on its own. Never call sg: on many Linux systems that is the shadow-utils group tool. Discovery order: the ZAP_AST_GREP environment variable, then each PATH entry, then ~/.cargo/bin, ~/.local/bin, /usr/local/bin and /usr/bin (a desktop-launched zapgui often lacks the shell's PATH, and ~/.cargo/bin is where cargo install ast-grep --locked puts it). Probe before first use by capability, not version: --version must start with ast-grep, and scan --help must mention --inline-rules and --json. Cache only successes (in a OnceLock), so installing it while zapgui runs needs no restart. Under cfg(test) a thread-local override replaces the path so tests can point at a fake script.

Failure modes. Each is one clause with no semicolon, fails the step in play, and writes nothing, so it arrives in the usual "step N of M (astgrep FOLDER) failed: ..." sentence. Not found: "astgrep: ast-grep was not found (looked on PATH and in ~/.cargo/bin), install it with cargo install ast-grep --locked and retry". Too old: "astgrep: the ast-grep at PATH is too old (it needs scan --inline-rules and --json), update it with cargo install ast-grep --locked". Non-zero exit: "astgrep: ast-grep failed: " plus the first 200 characters of stderr on one line. Over 30 s, killed: "astgrep: ast-grep took longer than 30 s under FOLDER, try a narrower folder". zapcli does not check availability: zapgui runs the binary, possibly with a different PATH.

What it runs. One scan with one inline rule, JSON output, no rewriting. The rule in words: language rust; a node matches when its text equals the old name (a regex anchored at both ends) and its kind is identifier, type_identifier, field_identifier or shorthand_field_identifier; severity set to hint so a match never turns the exit code non-zero. The folder is the last argument, and the command is built as an argument vector, never through a shell. Its working directory is a private empty folder, ~/.cache/zap/astgrep-cwd made 0700: ast-grep reads sgconfig.yml from where it starts, a config can register custom language libraries, and a project must not get to plant one. Drain stdout and stderr on their own threads and poll for exit, so a full pipe cannot hang it, and cap stdout at 64 MB.

Check the real output before coding. Run the installed binary once on a scratch file containing a function name, a struct, a field, a shorthand field in a pattern, an enum variant, a macro argument, a path segment, a generic parameter, a lifetime and a loop label. Confirm the node kinds in the rule against what comes back and adjust the list if they differ. If 'a shows up as an identifier match, add a clause that excludes matches whose parent is a lifetime or label, since renaming a should not rename 'a. Confirm the output carries the file path and byte offsets for each match (range.byteOffset start and end at the time of writing), whether it prints a stream of objects or one array (accept both), and whether file paths come back absolute. No byte offsets means "too old". Save the real output as test fixtures.

From matches to edits, in astgrep.rs. Parse matches into file, start and end; drop files with a path component target or .git, or any dot-directory, relative to the folder, since ast-grep honours .gitignore but zap does not rely on there being one. Per file, read it through load_once like every other step, so the snapshot holds the disk text, then require the text at start..end to equal the old name, using get and not slicing; a mismatch (stale offsets, a file changed meanwhile, an offset inside a character) fails the step with "astgrep: the file changed while it was being scanned: PATH". Sort the ranges, reject overlaps, build the new text piecewise. A matched file that fails the HiddenSet check fails the step naming it; skipping it would leave a half rename. Zero matches fails with "astgrep: no identifier named X found under FOLDER". Caps: 200 files and 4 MB of changed text in total, else "astgrep: N files match, try a narrower folder". The result is a list of per-file changes (path, before, after, occurrences) sorted by path; the type lives in astgrep.rs.

One step, whole rename or nothing. A half-applied rename does not compile, so the unit of approval is the whole rename: one AppliedStep, one block in the review column, one mark.
